# Spec 09 — Product Verification & Testing

> **Status**: Draft
> **Depends on**: Spec 02 (Agent Execution), Spec 06 (Sprint Cycle), Spec 08 (Product Storage)
> **Unlocks**: Tier 2 runtime verification (post-MVP)

---

## Problem

Agents build code. Nobody checks if it works. The board sees a preview iframe that might be a blank page. There is no build gate, no test gate, no verification of any kind between "Developer wrote files" and "board reviews the product."

The Tester agent (Quinn) has a SOUL prompt but no tools and no tasks. The orchestrator marks tasks as done based on agent completion, not product correctness.

---

## Design

Two-layer verification:

**Layer 1 — Orchestrator Gates (automated, no agent needed)**
- Build check: `npm run build` — pass/fail on exit code
- Test check: `npm run test` — pass/fail on exit code
- These are non-negotiable. Every sprint runs through both.

**Layer 2 — Tester Agent (Quinn) writes test code**
- Quinn writes actual test files as part of the sprint
- Runs **in parallel** with Developer (Option B)
- CTO produces the plan → Orchestrator creates Developer tasks + one Tester task
- Tester writes tests from the plan/spec, not from the implementation
- Tests become part of the product codebase, committed to git, persist across sprints
- Sprint 1 tests are Sprint 2's regression suite

**Tier 2 — Runtime Verification (POST-MVP)**
- Playwright headless browser hits the running app
- Screenshot + console errors + network failures + LLM judgment
- Deferred due to ~200MB Playwright dependency

## Tester Agent (Quinn) — How It Works

### When Quinn Runs

Quinn runs **in parallel** with Developer during sprint execution. The orchestrator creates tasks like:

```
Developer tasks (from CTO plan):
  - "Build menu page with items and prices"
  - "Build cart with add/remove functionality"
  - "Build checkout form with validation"

Tester task (auto-generated by orchestrator):
  - "Write happy-path tests for: menu page displays items with prices,
     add-to-cart updates cart count, checkout form validates required fields"
```

The Tester task is derived mechanically from the CTO's plan — the orchestrator extracts the feature list and formats it as test requirements. The CTO doesn't need to write test-specific tasks.

### What Quinn Receives

Quinn's prompt context includes:
- **CTO's plan artifact** — what features are being built this sprint
- **Sprint goals** — high-level description of what the product should do
- **Existing test files** (Sprint 2+) — so Quinn doesn't duplicate or contradict
- **package.json** — so Quinn knows the stack and can pick the right test framework

Quinn does NOT receive Developer's code (they run in parallel). Quinn writes tests from the spec, not the implementation. This is intentional — tests verify intent, not implementation details.

### What Quinn Produces

**Test files** co-located with source:

```
src/
  components/
    Menu.tsx                 ← Developer writes
    Menu.test.tsx            ← Quinn writes
    Cart.tsx                 ← Developer writes
    Cart.test.tsx            ← Quinn writes
  api/
    menu.ts                  ← Developer writes
    menu.test.ts             ← Quinn writes
```

**Test config** (if not already present):

Quinn checks if test infrastructure exists. If not, Quinn:
1. Installs test dependencies: `npm install -D vitest @testing-library/react @testing-library/jest-dom`
2. Creates `vitest.config.ts` with sensible defaults
3. Adds `"test": "vitest run"` to package.json scripts

### Framework Detection

Quinn reads `package.json` and picks the test framework:

| Stack Detected | Test Runner | Testing Library |
|----------------|-------------|-----------------|
| Next.js / React | vitest | @testing-library/react |
| Vite + React | vitest | @testing-library/react |
| Vite + Vue | vitest | @vue/test-utils |
| Express API | vitest | supertest |
| Plain Node.js | vitest | (none) |
| Python Flask | pytest | pytest-flask |

vitest is the default for all JS/TS projects. It's fast, Vite-native, and Jest-compatible.

### Test Scope — Happy Path Only

Quinn writes **3-8 test files per sprint**, focusing on:

- **Component rendering** — "Menu renders a list of items with prices"
- **User interactions** — "Clicking Add to Cart increments the cart badge"
- **API shape** — "GET /api/menu returns an array of items with name and price fields"
- **Form validation** — "Checkout form shows error when email is empty"

Quinn does NOT write:
- Exhaustive edge case tests
- Implementation detail tests (internal state, private methods)
- Snapshot tests (brittle, low value)
- CSS/visual tests (that's Tier 2, post-MVP)
- Performance tests

### Naming Convention

```
[Component].test.tsx    — React component tests
[module].test.ts        — utility / API tests
```

Each test file has a top-level `describe` matching the feature name from the CTO's plan.

## Orchestrator Gate — Build + Test Check

### When It Runs

After BOTH Developer and Tester complete their tasks. The orchestrator waits for both to finish (parallel execution), then runs the gate.

### Gate Implementation

New function in orchestrator: `runVerificationGate(companyId: string)`

```
Step 1: Detect project type
  Read package.json → determine build and test commands
  Fallback: skip gate if no package.json found (static site)

Step 2: Install dependencies
  Run: npm install (if node_modules missing or package.json changed)
  Timeout: 120 seconds
  Failure: GATE_FAIL with "dependency installation failed"

Step 3: Build check
  Run: npm run build
  Timeout: 120 seconds
  Capture: stdout, stderr, exit code
  exit code 0 → proceed
  exit code != 0 → GATE_FAIL with build errors

Step 4: Test check
  Run: npm run test (if "test" script exists in package.json)
  Timeout: 120 seconds
  Capture: stdout, stderr, exit code, test summary
  exit code 0 → GATE_PASS
  exit code != 0 → GATE_FAIL with test failures
  No test script → skip (warn, don't fail)
```

### Gate Result

```typescript
type GateResult = {
  passed: boolean;
  buildResult: {
    exitCode: number;
    stdout: string;
    stderr: string;
    durationMs: number;
  };
  testResult: {
    exitCode: number;
    stdout: string;
    stderr: string;
    durationMs: number;
    summary: string;       // "5 passed, 2 failed, 1 skipped"
  } | null;                // null if no test script
};
```

### Storing Gate Results

Gate results are stored as artifacts (Spec 08):

```typescript
addArtifact("orchestrator", "output", "Verification Gate — Sprint 1", gateResultSummary);
```

This gives the board visibility into build/test status without seeing raw logs.

## Failure Loop

When the gate fails:

```
Gate fails (build error or test failure)
        │
        ▼
  Orchestrator creates retry task for Developer:
    title: "Fix: 2 test failures in Menu.test.tsx"
    context:
      - Which tests failed (names + file paths)
      - Error messages + stack traces
      - The test file content (so Developer can see what's expected)
      - Instruction: "Fix the implementation to pass these tests.
        Do NOT modify test files."
        │
        ▼
  Developer fixes code
        │
        ▼
  Orchestrator reruns gate
        │
        ├── PASS → continue to preview
        └── FAIL → retry (max 2 attempts)
                      │
                      └── After 2 failures → escalate to CTO
                          CTO decides:
                            a) Adjust the plan (scope was wrong)
                            b) Modify tests (test was unreasonable)
                            c) Skip failing tests (ship anyway, log tech debt)
```

### Critical Rule

**Developer fixes the code, not the tests.** Tests represent the spec. If the test says "Menu should display items" and the code doesn't, the code is wrong.

Exception: CTO can override this if the test itself is wrong (testing something not in the plan). CTO is the only agent that can authorize test modification.

## Orchestrator Integration

### New Task Type: `verification`

Add to the existing task kinds in Spec 04:

```
kind: "technical_plan" | "acceptance_spec" | "implementation" | "preview" |
      "review" | "specialist" | "custom" | "test" | "verification"
```

- `test` — Tester agent task (write test files)
- `verification` — orchestrator-level gate (run build + tests)

### Execution Flow Change

Current flow (Spec 02):

```
plan → acceptance → build → preview → review
```

New flow:

```
plan → acceptance → [build + test (parallel)] → verification gate → preview → review
```

The orchestrator creates:
1. Developer tasks (kind: `implementation`) — from CTO's plan
2. One Tester task (kind: `test`) — auto-generated from plan
3. Both run in parallel
4. When both complete → orchestrator runs verification gate (kind: `verification`)
5. Gate passes → preview task starts
6. Gate fails → Developer retry loop

### Task Dependencies

```
CTO plan task
  ├── Developer task 1 (implementation)   ─┐
  ├── Developer task 2 (implementation)    ├── all must complete
  ├── Developer task 3 (implementation)    │   before gate runs
  └── Tester task (test)                  ─┘
                                           │
                                           ▼
                                  Verification gate task
                                           │
                                           ▼
                                     Preview task
```

## Sprint 2+ Regression

This is the payoff. Quinn's tests accumulate:

**Sprint 1:** Quinn writes 5 test files for menu + cart
**Sprint 2:** Quinn writes 3 new test files for checkout + payments

When the gate runs in Sprint 2, it executes ALL tests — Sprint 1's 5 files + Sprint 2's 3 files. If Developer broke the menu while building checkout, Sprint 1's tests catch it.

No extra work needed. Regression testing is automatic because:
- Tests live in the workspace (committed via Spec 08)
- `npm run test` runs everything in the project
- Old tests catch old regressions

## Tester Agent Configuration

### SOUL Update

Quinn's SOUL prompt (`.opencode/prompts/tester-soul.txt`) needs updating to reflect the new responsibilities:

```
You are Quinn, the QA specialist at {company}.

Your job is to write test code that verifies the product works correctly.
You receive the CTO's plan describing what features are being built.
You write happy-path tests that verify the core user-facing behavior.

Rules:
- Write tests from the SPEC, not from the implementation
- Use vitest + @testing-library/react for React projects
- Co-locate test files next to source files (Menu.test.tsx next to Menu.tsx)
- Focus on user-visible behavior, not implementation details
- 3-8 test files per sprint, happy path only
- Set up test infrastructure (vitest.config.ts, dependencies) if missing
- Name test files: [Component].test.tsx or [module].test.ts
- Each test file has a describe block matching the feature name

You do NOT:
- Write snapshot tests
- Test CSS or visual appearance
- Test internal state management details
- Write more than 10 test files per sprint
- Modify existing test files from previous sprints (unless CTO instructs)
```

### Permissions

Quinn needs:
- `can_edit_files: true` — writes test files
- `can_run_shell: true` — runs `npm install -D` for test dependencies
- `can_write_code: true` — writes TypeScript/JavaScript test code

These match Quinn's existing permissions in `opencode.json`.

## Gate Runner Implementation

New file: `apps/api/src/verification-gate.ts`

```typescript
interface GateConfig {
  workspacePath: string;
  buildTimeout: number;     // default: 120_000 ms
  testTimeout: number;      // default: 120_000 ms
  installTimeout: number;   // default: 120_000 ms
}

interface GateResult {
  passed: boolean;
  buildResult: CommandResult;
  testResult: CommandResult | null;
  installResult: CommandResult;
  totalDurationMs: number;
}

interface CommandResult {
  exitCode: number;
  stdout: string;
  stderr: string;
  durationMs: number;
}

// Main entry point — called by orchestrator after Developer + Tester finish
async function runVerificationGate(config: GateConfig): Promise<GateResult>

// Helpers
function detectProjectType(workspacePath: string): ProjectType
function getBuildCommand(projectType: ProjectType): string
function getTestCommand(workspacePath: string): string | null
function parseTestSummary(stdout: string): string
function formatFailureContext(gateResult: GateResult): string
```

All commands run via `child_process.execFile` with timeouts. stdout/stderr captured for artifact storage and Developer retry context.

## Post-MVP: Tier 2 — Runtime Verification

When we add Playwright (~200MB dependency):

```
Gate passes (Tier 1)
    │
    ▼
Detect project type → pick start command
    │
    ▼
Start app as child process (random port)
    │
    ▼
Wait for port to bind (poll, 30s timeout)
    │
    ▼
Playwright navigates to localhost:{port}
    ├── Screenshot landing page
    ├── Collect console.error messages
    ├── Collect network failures (4xx, 5xx)
    ├── Check: is <body> empty? (blank page detection)
    └── Check: any unhandled JS errors?
    │
    ▼
LLM evaluates:
    Input: screenshot + errors + sprint goals
    Output: PASS/FAIL + reasoning
    │
    ├── PASS → preview + board review
    └── FAIL → Developer retry with screenshot + errors
```

Additional post-MVP capabilities:
- Screenshot comparison between sprints (visual regression)
- Accessibility check (axe-core)
- Performance budget (Lighthouse scores)
- Smoke test flows (Playwright navigates critical user paths)

## Key Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Tester runs parallel with Developer (Option B) | Tests from spec, not implementation. True verification. |
| 2 | Orchestrator creates Tester task automatically | CTO doesn't need to think about test tasks. Mechanical split. |
| 3 | Happy-path tests only (3-8 files per sprint) | Full coverage is expensive and brittle. Happy path catches real issues. |
| 4 | vitest as default test runner | Fast, Vite-native, Jest-compatible, works for all JS/TS projects. |
| 5 | Developer fixes code, not tests | Tests are the spec. Code must conform. CTO is the only override. |
| 6 | Max 2 retries then escalate to CTO | Prevents infinite loops. CTO makes judgment calls. |
| 7 | Tests accumulate across sprints | Sprint 1 tests catch Sprint 2 regressions. Free regression suite. |
| 8 | Tier 2 (Playwright) deferred to post-MVP | 200MB dependency, sandbox complexity. Tier 1 is sufficient for MVP. |
| 9 | Gate results stored as artifacts | Board visibility into quality without raw build logs. |
| 10 | Co-located test files | `Menu.test.tsx` next to `Menu.tsx`. Standard convention. Easy to find. |
